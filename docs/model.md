# logreg-synthetic-0.1: обучаемая логистическая регрессия

Первая обученная модель сервиса. Отвечает на `POST /api/v1/score` в прежнем формате, `model_version = logreg-synthetic-0.1`.
Обучена **только на синтетических данных**: это рабочий прототип конвейера (данные → обучение → артефакт → расчёт в сервисе
и в backend), а не модель, откалиброванная на реальных дефолтах.

| Что | Где |
|---|---|
| Генератор данных | `ml/generate.py` |
| Обучение, экспорт, метрики, контрольные входы | `ml/train.py` |
| Признаки (общие для обучения и сервиса) | `app/features.py` |
| Расчёт в сервисе по JSON, без sklearn | `app/model.py` |
| Артефакт для backend | `models/logreg-synthetic-0.1.json` |
| Метрики | `models/logreg-synthetic-0.1.metrics.json`, [model-metrics.md](model-metrics.md) |
| Контрольные входы и ожидаемые ответы | `data/conformance/logreg-synthetic-0.1.json` |
| Перенос в C# | [backend/logreg.md](backend/logreg.md) |
| Тесты | `tests/test_model.py` |

Воспроизведение (около 5 секунд):

```bash
pip install -r requirements-train.txt
python -m ml.generate   # data/synthetic/applications.csv.gz — только чтобы посмотреть данные, обучению файл не нужен
python -m ml.train      # перезаписывает models/, data/conformance/logreg-synthetic-0.1.json, docs/model-metrics.md
pytest -q
```

Тот же seed даёт тот же набор (sha256 записан в артефакт и метрики) и те же коэффициенты; `tests/test_model.py` переобучает модель
и сверяет с артефактом.

## 1. Данные

`ml/generate.py`, seed `20261025`: 20 000 компаний, у каждой 1–4 заявки, всего 29 886 заявок, дефолтов 9,1 %.

- У компании есть ненаблюдаемое качество `q ~ N(0, 1)`. Оно сдвигает выручку, долю расходов, долговую нагрузку, вероятность просрочек,
  списаний, налогового долга, блокировок и исполнительных производств. Поэтому признаки с ним связаны, но полностью его не раскрывают.
- Заявки одной компании отличаются суммой (доля выручки), сроком 6–60 мес., ставкой 17–24 % и залогом. Платёж по заявке — аннуитет.
- Скрытая PD заявки — сигмоида от «настоящих» величин: нагрузка по настоящей прибыли (ступень около 0,6), расходы выше 90 % выручки,
  возраст меньше 12 и 24 мес., просрочки до 180 дней, списания, налоговый долг и блокировки, до трёх производств ФССП, сумма к выручке,
  залог, вклад `q` и шум `N(0; 0,4)`. Свободный член подобран так, что средняя PD = 9 %.
- **Исход случайный:** `default_12m ~ Bernoulli(скрытая PD)`. Одинаковые признаки могут дать разные исходы.
- Наблюдаемые данные неполные и с шумом: нет прибыли у ~12 % (у молодых чаще), нет расходов у ~8 %, нет ответа БКИ, ФНС или ФССП у ~3 %
  каждого. Отчётная прибыль отличается от настоящей на ±10 %.

Что **не попадает** в признаки:
- скрытые столбцы генератора `_quality`, `_true_pd`, `_true_profit` и сам `default_12m`. Обучение строит признаки из запроса
  `/api/v1/score` (`ml.generate.to_request`), где этих полей нет, и проверяет это явно;
- события после даты заявки: все поля описывают состояние на момент подачи;
- баллы и грейды rules-0.3: генератор и обучение их не вызывают, разметка — только `default_12m`.

## 2. Признаки

16 признаков из полей текущего запроса. Формулы для C# — в `features[*].formula` артефакта.

| Признак | Формула | Пропуск |
|---|---|---|
| `log_revenue` | ln(1 + выручка) | — |
| `expense_ratio` | расходы / выручка, [0; 2] | нет расходов или выручка 0 |
| `profit_margin` | прибыль / выручка, [−1; 1] | нет прибыли или выручка 0 |
| `debt_load` | (текущие платежи + новый платёж) × 12 / прибыль, [0; 5]; 5 при прибыли ≤ 0 | нет прибыли |
| `amount_to_revenue` | сумма / выручка, [0; 5]; 5 при выручке 0 | — |
| `log_amount` | ln(сумма) | — |
| `term_months` | срок | — |
| `log_business_age` | ln(1 + возраст, мес.) | — |
| `overdue_months` | min(макс. просрочка за 24 мес., 360) / 30 | нет ответа БКИ |
| `write_offs` | списания 1/0 | нет ответа БКИ |
| `no_credit_history` | нет истории, активных и закрытых кредитов 1/0 | нет ответа БКИ |
| `log_tax_debt` | ln(1 + налоговый долг) | нет ответа ФНС |
| `blocked_accounts` | блокировка счетов 1/0 | нет ответа ФНС |
| `enforcement_count` | min(открытые производства, 10) | нет ответа ФССП |
| `log_enforcement_amount` | ln(1 + сумма производств) | нет ответа ФССП |
| `collateral` | залог предложен 1/0 | — |

Обработка пропусков — как в `SimpleImputer(strategy="median", add_indicator=True)`: пропуск заменяется медианой train
(`impute_value`), и для каждого признака, у которого в train были пропуски, добавляется столбец `missing:<имя>` = 1/0.
Таких столбцов 10, всего столбцов модели 26. Если пропуск встретится в признаке без индикатора (в train их не было), он просто
заменяется медианой.

## 3. Обучение

`Pipeline`: `SimpleImputer(median, add_indicator=True)` → `StandardScaler` → `LogisticRegression(lbfgs, L2)`.

- Разбиение `GroupShuffleSplit` по `company_id`, seed 42: train 70 % компаний, validation 15 %, test 15 %. Все заявки компании
  в одной части, пересечений нет (проверяется при обучении и в тестах).
- `C` из сетки 0,003…3 выбирается по log loss на validation (выбрано 0,03), модель обучается на train, test используется один раз.

## 5. PD → балл → грейд

```
pd    = 1 / (1 + exp(−(intercept + Σ coef[c] · z[c])))        # в ответе как есть, без округления
score = clamp(floor(100 · (0,32 − pd) / (0,32 − 0,02) + 0,5), 0, 100)
grade = A, если score ≥ 80; B ≥ 65; C ≥ 50; D ≥ 35; иначе E
```

Шкала линейная и обратна эвристике backend `PD = 0,02 + (100 − балл) / 100 × 0,30`. Балл 100 при PD ≤ 2 %, 0 при PD ≥ 32 %.
Границы грейдов не менялись (A 80–100, B 65–79, C 50–64, D 35–49, E 0–34) и соответствуют PD:

| Грейд | Балл | PD |
|---|---|---|
| A | 80–100 | ≤ 8,15 % |
| B | 65–79 | > 8,15 % и ≤ 12,65 % |
| C | 50–64 | > 12,65 % и ≤ 17,15 % |
| D | 35–49 | > 17,15 % и ≤ 21,65 % |
| E | 0–34 | > 21,65 % |

Ровно на границе (8,15 %, 12,65 % …) округление половины вверх даёт лучший грейд. Балл 80 / 65 / 50 / 35 соответствует PD 8 / 12,5 / 17 / 21,5 %.

Параметры (`pd_at_score_100`, `pd_at_score_0`, границы) лежат в артефакте (`score`, `grades`). Контрольные пары PD → балл
вплотную к границам — `score_mapping` в контрольных входах.

**Требует подтверждения:** формулу перевода PD в балл я не нашёл в общем ТЗ дословно и выбрал линейную, совместимую с эвристикой
backend. Если в ТЗ другая шкала (например, логарифмическая по шансам), поменяются только `score` в артефакте и эталоны; модель
и PD останутся теми же.

`probability_of_default` для этой версии — исходная PD модели, а не значение из балла. Это оценка вероятности `default_12m`,
откалиброванная **только на синтетике**. Это не вероятность одобрения.

## 6. Объяснения

Факторы ответа — вклады самой модели, сгруппированные по смыслу. Ручные баллы rules-0.3 в объяснение не попадают.

```
вклад[группа] = Σ coef[c] · z[c] по признакам группы и их индикаторам пропуска   # вклад в логит относительно средней заявки train (все z = 0)
impact        = clamp(round_half_away_from_zero(−points_per_logit · вклад), −100, 100)
points_per_logit = 100 / (0,32 − 0,02) · baseline_pd · (1 − baseline_pd) = 15,71,  baseline_pd = sigmoid(intercept) = 4,96 %
```

`impact` — примерная разница в баллах по сравнению со средней заявкой, взятая по наклону шкалы. Плюс снижает риск, минус повышает.
Это линейное приближение: сумма `impact` не равна баллу точно, и у заявок с баллом 0 или 100 вклады не обнуляются.
Сумма вкладов групп плюс `intercept` равна логиту точно (проверяется в тестах).

Группы (коды без префикса, как договорились для rules-0.3):

| Код | Название | Признаки |
|---|---|---|
| `revenue_size` | Размер выручки | `log_revenue` |
| `revenue_to_amount` | Сумма кредита к выручке | `amount_to_revenue`, `log_amount` |
| `loan_term` | Срок кредита | `term_months` |
| `expense_ratio` | Расходы к выручке | `expense_ratio` |
| `debt_load` | Долговая нагрузка и прибыльность | `debt_load`, `profit_margin` |
| `business_age` | Возраст бизнеса | `log_business_age` |
| `credit_history` | Кредитная история | `overdue_months`, `write_offs`, `no_credit_history` |
| `tax_debt` | Налоговая задолженность | `log_tax_debt`, `blocked_accounts` |
| `enforcement` | Исполнительные производства | `enforcement_count`, `log_enforcement_amount` |
| `collateral` | Обеспечение | `collateral` |

`revenue_size` и `loan_term` — новые коды, в rules-0.3 их нет. В ответе до 7 групп по убыванию |impact|, при равенстве по коду.
Тексты `client_explanation` зависят только от знака вклада; `value` — исходные данные заявки (как у rules-0.3, в инвариантной культуре).
`warnings` и `missing_data` формируются так же, как в rules-0.3.

Коэффициенты (на масштабированных признаках; плюс — выше риск):

| Признак | Коэф. | | Признак | Коэф. |
|---|---|---|---|---|
| `expense_ratio` | +0,518 | | `log_revenue` | −0,350 |
| `overdue_months` | +0,402 | | `log_business_age` | −0,237 |
| `debt_load` | +0,309 | | `collateral` | −0,153 |
| `log_amount` | +0,260 | | `term_months` | −0,115 |
| `write_offs` | +0,221 | | `profit_margin` | −0,111 |
| `log_tax_debt` | +0,220 | | `no_credit_history` | −0,094 |
| `blocked_accounts` | +0,180 | | | |
| `enforcement_count` | +0,166 | | | |
| `log_enforcement_amount` | +0,089 | | | |

Знаки ожидаемые. Отрицательный коэффициент у срока объясняется тем, что при той же сумме длинный срок даёт меньший платёж,
то есть меньшую нагрузку. Сам срок генератор в скрытую PD не включает.

## 7. Артефакт для backend

`models/logreg-synthetic-0.1.json` содержит всё для расчёта без sklearn:

| Поле | Что |
|---|---|
| `features[]` | порядок признаков, `formula`, `impute_value` (медиана train), `missing_indicator` |
| `missing_indicators.order` | для каких признаков добавляется `missing:<имя>` и в каком порядке |
| `columns` | итоговый порядок 26 столбцов: 16 признаков, затем 10 индикаторов |
| `scaling.mean`, `scaling.scale` | `z = (x − mean) / scale` по каждому столбцу, включая индикаторы |
| `coefficients`, `intercept` | логистическая регрессия |
| `pd` | формула PD |
| `score`, `grades` | перевод PD в балл и границы грейдов |
| `explanation` | группы, `baseline_pd`, `points_per_logit`, метод |
| `training` | seed, sha256 данных, `C`, версии sklearn и Python |

Порядок расчёта: признаки из запроса → `null` заменить на `impute_value`, индикаторы = 1 для `null` → `z` → логит → PD → балл → грейд → вклады групп.

## 8. Контрольные входы

`data/conformance/logreg-synthetic-0.1.json`, 32 случая:
- 5 демо-заявок на данных seed backend;
- по 4 заявки каждого грейда A–E из test;
- 7 вариантов «Ромашки»: без прибыли, без расходов, без БКИ, без ФНС, без ФССП, с убытком, с залогом.

Для каждого случая: `input` (запрос как от backend) и `expected`: PD и логит от sklearn (`predict_proba`, `decision_function`;
допуск 1e-9), балл, грейд, `features` (вектор до заполнения пропусков, `null` = пропуск), полный список факторов с текстами,
`warnings`, `missing_data`. Ещё есть `score_mapping` — 17 пар PD → балл → грейд у границ.
Сервис совпадает с sklearn до 1e-16. Тот же файл проверяет `scripts/smoke.py`, если сервис запущен с этой моделью.

## 9. Демо-заявки: rules-0.3 и logreg-synthetic-0.1

Решение посчитано копией `DecisionPolicy` (`scripts/backend_reference.py`).

| Заявка | rules-0.3 | logreg-synthetic-0.1 | Решение backend при logreg |
|---|---|---|---|
| «Ромашка», 1,5 млн / 12 мес. | 95 A, одобрение | 98 A, PD 2,5 % | одобрение, 19,5 %, без изменений |
| Кузнецов, 3 млн / 24 мес. | 55 C, одобрение с условиями: 2,4 млн, 22,5 % | 100 A, PD 0,9 % | **одобрение 3 млн под 19,5 %: сценарий «меньшая сумма» пропадает** |
| «Вектор», 8 млн / 24 мес. | 70 B, к менеджеру по сумме | 96 A, PD 3,2 % | к менеджеру по сумме, рекомендация «одобрить», без изменений |
| «Закат», 0,5 млн / 6 мес. | 0 E, отказ по стоп-факторам | 0 E, PD 95 % | отказ по стоп-факторам, без изменений |
| Петрова, 0,3 млн / 12 мес. | 25 E | 67 B, PD 11,8 % | в демо не подаётся: возраст 4 мес. не проходит проверку backend |

У Кузнецова расходы всего 44 % выручки и маржа 50 %. На синтетике таких компаний почти нет (доля расходов там 0,45–1,25,
медиана 0,82), а низкие расходы сильно снижают риск. Модель экстраполирует, и `expense_ratio` даёт +33 балла.
Это ограничение синтетических данных, а не ошибка расчёта. Если демо со сниженной суммой нужно сохранить, есть три пути:
переключить сервис на `rules-0.3`, поменять профиль Кузнецова в seed или добавить в генератор компании с низкими расходами.

## 10. Переход и паритет с backend

Backend при недоступности сервиса считает по своим правилам (`RulesFallback`), сейчас это rules-0.3. Если сервис ответит logreg,
решение будет зависеть от того, кто считал: у Кузнецова это A против C. Поэтому:

- В сервисе модель выбирается переменной `SCORING_MODEL`: `logreg-synthetic-0.1` (по умолчанию в коде и образе) или `rules-0.3`.
  `/health` и `model_version` показывают выбранную.
- `docs/backend/compose.scoring.yml` и `scripts/run_stand_checks.sh` ставят `SCORING_MODEL=rules-0.3`, пока backend не перенёс модель.
- Образ получает тег `logreg-synthetic-0.1`. Тег `rules-0.3` остаётся на прежнем образе. В общем compose — только тег конкретного
  коммита и только после зелёных тестов с обеих сторон, по договорённости от 24.10.2026.
- Перенос в C#: [backend/logreg.md](backend/logreg.md). После него резервный расчёт и сервис считают по одному артефакту
  и совпадают на контрольных входах.

## 11. Ограничения

- **Синтетика.** Данные, зависимости и доля дефолтов придуманы. Метрики показывают, что конвейер работает и модель восстанавливает
  заложенные связи, но ничего не говорят о качестве на реальных заявках. PD откалибрована только на синтетике.
- Модель линейная по признакам: ступень нагрузки около 0,6 и порог расходов 90 % она приближает плавно, а за пределами данных
  экстраполирует (пример — Кузнецов).
- Грейды распределены неравномерно (A — 74 %) из-за выбранной шкалы PD → балл и средней доли дефолтов 9 %.
- `impact` в объяснении — линейное приближение вокруг средней заявки, а не точное разложение балла.
- Проверка ЕГРЮЛ и `reported_revenue_rub` ФНС в модель не входят: по ЕГРЮЛ backend решает стоп-факторами, а сверку выручки
  генератор не моделирует.
