Статус: **сверено на данных backend, ждёт подтверждения бэкендером** (раздел 7). Пороги и баллы `rules-0.2` не менялись.

Что сравнивается: сервис `scoring` (`rules-0.2`) и встроенная модель backend (`rules-v1`), которую backend включает,
если сервис не ответил. Плюс решение кредитной политики backend при каждом из двух ответов: именно его видит клиент.

  окончательное подтверждение даст C#-тест из раздела 7.

## 2. Почему расходятся

Модели считают разные вещи, поэтому баллы несравнимы, а грейды совпадают только случайно.

| | Python `rules-0.2` | C# `rules-v1` (по коду) |
|---|---|---|
| Расходы к выручке | <70 % +15; 70–90 % −5; >90 % −20 | не учитываются |
| Выручка к сумме кредита | не учитывается | ≥4 +15; 2–4 +5; 1–2 −5; <1 −20 |
| Долговая нагрузка | <0,30 +20; 0,30–0,70 0; >0,70 −20 | <0,3 +10; 0,3–0,5 0; 0,5–0,7 −10; ≥0,7 −25 |
| Нет прибыли | −35 | нагрузка считается равной 9,99: −25 |
| Чистая прибыль не пришла | выручка − расходы | 10 % выручки, предупреждение `net_profit_missing` |
| БКИ, ФНС, ФССП | не учитываются, только `*_missing` в `warnings` | история −30..+15, налоги −30..+5, ФССП −10..0 |
| Возраст бизнеса | <6 −20; 6–11 −10; 12–36 0; >36 +10 | то же, но ровно 36 мес. уже +10 |
| Нехватка данных | нет выручки, расходов или платежей: балл 40, грейд D | расчёт идёт по тому, что есть |

По заявкам:

- **«Ромашка», 55 против 95.** Python штрафует расходы 85 % выручки (−5) и не видит чистую кредитную историю, налоги и выручку в 32 раза
  больше суммы: C# получает за них +35. Нагрузка 0,48 нейтральна в обеих моделях. Синтетические данные прошлой версии давали A только потому,
  что расходы там были 63 %.
- **«Кузнецов», 75 против 55.** Расходы 44 % дают в Python +15, а просрочка до 25 дней и налоговый долг 12 000 ₽, из-за которых сценарий
  задуман как «с условиями», Python не видит. C# снимает за них −10 и даёт за выручку/сумму 3,2 только +5.
- **«Вектор», 35 против 70.** Нагрузка 1,20 в обеих моделях максимальный штраф (−20 и −25). Дальше C# добавляет +35 за чистую историю,
  налоги и выручку, а Python снимает ещё −5 за расходы 89 %. В итоге Python D (35, нижняя граница), C# B.
- **«Закат».** Обе модели дают E, но это не важно: backend отказывает по стоп-факторам ещё до грейда (налоговый долг 700 000 ₽,
  блокировка счетов, просрочка 95 дней, ФССП 1,4 млн).
- **«Петрова».** Python не строит оценку без расходов (D, менеджер). C# достраивает прибыль как 10 % выручки (10 000 ₽ в месяц),
  получает нагрузку 2,82 и −20 за возраст: E, отказ.

Что проверено по коду C# из прежних предположений (раньше C# считался по описанию):

1. Выручка к сумме берётся по годовой выручке: **да**.
2. Без чистой прибыли месячная прибыль = 10 % годовой выручки / 12: **да**.
3. Прибыль ≤ 0 даёт −25 за нагрузку: **да** (нагрузка подставляется как 9,99).
4. Без `monthly_debt_payments_rub` фактор нагрузки пропускается: **нет**, такого случая не бывает: в backend поле не nullable, отправляется всегда.
5. Заблокированные счета дают ещё −15 к налоговому фактору: **да**.
6. Возраст «то же самое»: **не совсем**, ровно 36 месяцев C# считает как «больше трёх лет» (+10), Python как 0.

## 3. Влияние на итоговое предложение

В общем `docker-compose.yml` backend по умолчанию `SCORING_MODE=External`: решение строится на ответе сервиса скоринга,
C#-правила включаются только при его недоступности. Сейчас там поднимается заглушка backend `scoring/app.py` (`stub-rules-1.0`),
и она повторяет `rules-v1`, поэтому демо пока идёт по C#-столбцу. Как только заглушку заменит этот сервис, клиент увидит столбец «Python»:

| Клиент | Задумано (C#) | Будет с Python | Для клиента |
|---|---|---|---|
| `client_good` | одобрено как просили, 19,5 %, 138 593,06 ₽/мес | одобрено **с условиями**: ставка 22,5 %, 140 752,78 ₽/мес | сценарий «автоодобрение» пропадает, платёж +2 159,72 ₽/мес |
| `client_medium` | 2,4 млн под 22,5 %, 125 100,96 ₽/мес, объяснение «сумма снижена» | **3 млн под 21 %**, 154 156,95 ₽/мес, без условий | сценарий «изменённые условия» пропадает |
| `client_manual` | менеджер, рекомендация «одобрить»; демо-менеджер при одобрении: 8 млн под 21 %, 411 085,21 ₽/мес | менеджер, рекомендация «с условиями»; при одобрении: 8 млн под **24,5 %** и выписка за 6 мес., 424 967,84 ₽/мес | статус тот же, условия хуже |
| `client_bad` | отказ, 4 стоп-фактора | то же | без изменений |
| `client_new` | `400` при подаче | то же | без изменений |

Отказ демо-менеджера (50 %) у «Вектора» одинаковый при обоих грейдах. Ни один из интеграционных тестов backend этого не ловит:
конвейер там проверяется в режиме `Rules`, а внешний скоринг заглушкой с фиксированным ответом 82 / A.

## 4. Контракт

- Все пять запросов в том виде, как их отправляет backend (с `23.0` и `19.5` в ставке, `null` в пропусках, лишними полями), проходят строгую
  валидацию сервиса: `200`. Пример запроса из `docs/scoring-contract.md` backend тоже проходит (55 / C: это та же «Ромашка»).
- Повтор одного запроса даёт побайтно одинаковый ответ, `request_id` возвращается без изменений.
- Ответ содержит всё, что читает `HttpScoringService.Map`: целый `score`, грейд A..E, 3–4 фактора с целым `impact`, `title` и `client_explanation`,
  `probability_of_default: null`, списки `warnings` и `missing_data`.
- Backend не может отправить значение, которое сервис отвергнет: выручка, расходы и платежи в домене не меньше 0, выручку ≤ 0 отсекает
  этап Validate, сумма и срок ограничены продуктом. Это важно: на любой `4xx` backend не повторяет запрос и **молча** считает C#-правилами
  (`source = RulesFallback`, предупреждение `external_scoring_unavailable`), а это другие грейды из таблицы выше.
- Мелочи, которые стоит согласовать, но которые не мешают демо:
  - коды факторов Python уже начинаются с `factor_`, а backend добавляет префикс ещё раз: в причинах решения `factor_factor_debt_load`.
    Клиенту коды не видны (фронтенд показывает `title` и `explanation`), в примере контракта коды без префикса;
  - C# пишет «прибыль отсутствует» у «Закат», хотя прибыль 100 000 ₽ есть: так выводится любая нагрузка ≥ 9,99;
  - на битый JSON сервис отвечает `400`, но ключ в `details` позиция символа (`"15"`), а не имя поля.

## 5. Нехватка данных

Из обязательных для Python полей (выручка, расходы, платежи по кредитам) backend на деле может не прислать только **расходы**:
выручка и платежи в C# не nullable. Ещё бывают `null` у чистой прибыли, у `fns.reported_revenue_rub` и у блоков ФНС и ФССП.

| Чего нет | Python | C# | Решение backend |
|---|---|---|---|
| `expenses_rub` («Петрова») | 40 / D, `missing_data: [expenses_rub]` | считает дальше | при Python менеджер, при C# по грейду |
| `net_profit_rub` | прибыль = выручка − расходы | прибыль = 10 % выручки | на «Ромашке» 7,2 млн против 4,8 млн в год: у C# нагрузка 0,72 и 70 / B вместо 95 / A |
| блок `fns` или `fssp` | без влияния на балл, `fns_missing` / `fssp_missing` | фактор пропускается | менеджер при любом грейде (`checks_missing`) |
| блок `egrul` или `credit_bureau` | без влияния на балл | фактор пропускается | до скоринга не доходит: менеджер на этапе Enrich |

Когда расходы не пришли, а заявка дойдёт до скоринга: сумма до 3 млн на оборотный, экспресс или овердрафт (для больших сумм и кредитной
линии backend сам требует расходы). В seed это только «Петрова», и сейчас её не пускает возраст. **15.12.2026 ей исполнится 6 месяцев**,
экспресс и овердрафт станут доступны, и тогда Python отправит её к менеджеру, а C# откажет.

Некорректный ввод (строка или `true` вместо числа, `NaN`, `Infinity`, сумма 0, срок 0 или 12,5, выручка 0, отрицательные расходы
или возраст, нет раздела `application`, пустой `request_id`, битый JSON, пустое тело) даёт `400` с полем в `details`, ни одного `500`.

## 6. Насколько устойчивы исходы

- C#: нагрузка «Ромашки» и «Кузнецова» 0,48, до границы штрафа 0,5 совсем немного. «Кузнецов» с 3,2 млн вместо 3 млн или со сроком 22 мес.
  вместо 24 получает D и уходит к менеджеру. «Ромашка» остаётся A и при 1,65 млн.
- Python: «Вектор» стоит на нижней границе D (35), расходы 88,9 % при пороге 90 %. Если расходы выйдут за 90 % выручки, балл упадёт до 20 (E), то есть отказ.
- Возраст бизнеса считается на дату заявки: на демо-компаниях до следующей границы далеко, кроме «Петровой» (см. выше).
