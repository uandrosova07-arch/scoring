# Python и резервные C#-правила: согласование rules-0.3

Статус: **сервис scoring и резервные правила backend считают по `rules-0.3`** (правки в C# внесены, [backend/README.md](backend/README.md)).
Проверка в полном процессе на стенде: [stand-checks.md](stand-checks.md).
За основу взяты резервные правила backend `rules-v1`, которые бэкендер подтвердил тестами на данных seed.
Спецификация: [calculation.md](calculation.md).

## Что согласовано

- **Факторы и пороги** как в `rules-v1`: возраст бизнеса, выручка к сумме кредита, долговая нагрузка, кредитная история (БКИ),
  налоговая задолженность и блокировки (ФНС), исполнительные производства (ФССП), залог. Тексты для клиента дословно те же.
- **Расходы** учитываются одинаково с обеих сторон: фактор `expense_ratio` (расходы > 90 % выручки: −10, бонуса нет)
  и прибыль = выручка − расходы, если чистая прибыль не пришла.
- **Пропуски** как у backend: фактор без данных не считается, в `warnings` предупреждение, расчёт продолжается.
  Балла 40 / D при нехватке данных больше нет.
- **Коды факторов без префикса** `factor_`: `business_age`, `revenue_to_amount`, `expense_ratio`, `debt_load`, `credit_history`,
  `tax_debt`, `enforcement`, `collateral`. В причинах решения backend сам даёт `factor_debt_load` и т. п., двойного префикса нет.
- **PD** по формуле backend, `model_version` `rules-0.3` с обеих сторон.

## Демо-заявки

Запросы из seed backend (`data/requests/*.json`), те же продукты, суммы и сроки, что в общем демо, возраст бизнеса на 23.10.2026.
Python — ответ запущенного сервиса `rules-0.3`, C# — код backend как есть (`rules-v1`, без правок).

| Заявка | Python `rules-0.3` | C# `rules-v1` | Решение банка (одинаковое при обоих ответах) |
|---|---|---|---|
| ООО «Ромашка», оборотный, 1,5 млн на 12 мес. | 95 / A | 95 / A | одобрено: 1,5 млн под 19,5 %, 138 593,06 ₽/мес |
| ИП Кузнецов, оборотный, 3 млн на 24 мес. | 55 / C | 55 / C | с условиями: 2,4 млн под 22,5 %, 125 100,96 ₽/мес, «сумма снижена» |
| ООО «Вектор», оборотный, 8 млн на 24 мес. | 70 / B | 70 / B | менеджер (сумма выше лимита 5 млн), рекомендация «одобрить»; демо-менеджер при одобрении: 8 млн под 21 % |
| ООО «Закат», экспресс, 0,5 млн на 6 мес. | 0 / E | 0 / E | отказ: налоговый долг, блокировка счетов, просрочка 95 дней, ФССП |
| ИП Петрова, экспресс, 0,3 млн на 12 мес. | 25 / E | 25 / E | в демо до скоринга не доходит: `400` при подаче (бизнесу 4 месяца) |

Балл, грейд, PD и решение совпадают у всех пяти уже с текущим C#, включая причины решения
(`risk_grade`, `factor_credit_history`, …). Пока в C# нет правок, отличается только набор факторов: у Python есть `expense_ratio`
(у «Закат» −10, но балл и так упирается в 0), а у «Петровой» предупреждение `expenses_missing`. Все три сценария, которые ломал
`rules-0.2` («Ромашка», «Кузнецов», «Вектор»), снова дают задуманный исход.

предупреждения, `missing_data`. Ожидаемое посчитано копией C# с правками `rules-0.3` (`scripts/backend_reference.py`), а не сервисом.

| ЕГРЮЛ или выручки по отчётности ФНС | в баллах не участвуют, только `missing_data` | так же |

Выручку, текущие платежи, возраст бизнеса и новый платёж backend присылает всегда; `null` в них сервис отклоняет с `400`
(`tests/test_backend_contract.py`).

## Где текущий C# ещё отличается

Пока правки не внесены в `RuleBasedScoringService`, балл и грейд различаются только в трёх случаях эталона из 63,
и все три связаны с расходами. Решение банка для заявки «Ромашки» (оборотный 1,5 млн на 12 мес.) при таких данных:

| Случай | `rules-0.3` | C# `rules-v1` |
|---|---|---|
| нет чистой прибыли, расходы есть | 95 / A: одобрено под 19,5 %, 138 593,06 ₽/мес | 70 / B: одобрено под 21 %, 139 670,66 ₽/мес |
| расходы чуть больше 90 % выручки | 85 / A: одобрено под 19,5 % | 95 / A: то же решение |
| нет прибыли, расходы больше выручки | 60 / C: с условиями под 22,5 %, 140 752,78 ₽/мес | 70 / B: одобрено под 21 %, 139 670,66 ₽/мес |

В демо ни один из этих случаев не встречается: у seed-компаний прибыль есть, а расходы больше 90 % только у «Закат», которому
отказывают по стоп-факторам. Чтобы совпадение было полным на любых входах, нужны правки из [backend/README.md](backend/README.md).

## Почему расходился rules-0.2

`rules-0.2` считал свои факторы (расходы −5..+15, нагрузка −20..+20, возраст) и не смотрел на БКИ, налоги и выручку к сумме.
На цифрах seed это давало «Ромашке» C вместо A (условия под 22,5 % вместо автоодобрения), «Кузнецову» B вместо C
(3 млн под 21 % вместо 2,4 млн под 22,5 %), «Вектору» D вместо B. При нехватке данных он ставил 40 / D, а C# считал дальше.
Коды факторов были с префиксом `factor_`, поэтому в причинах решения получалось `factor_factor_debt_load`.
