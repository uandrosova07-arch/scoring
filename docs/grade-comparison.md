# Согласование грейдов: Python-сервис и резервные C#-правила

Статус: **черновик для согласования с бэкендером**. Нужно, чтобы на демонстрационных компаниях Python и резервный расчёт backend
давали один и тот же грейд: тогда демо не зависит от того, отвечает ли `scoring`.

Резервные правила (`rules-v1`) я посчитал **по их описанию** в `docs/decision-logic.md`, а не по коду C#.
Поэтому столбцы «C# (по описанию)» нужно проверить: прогоните `input` из `data/demo_companies.json` через свой расчёт и сверьте.

## 1. Демонстрационные компании

| Компания | Python: балл | Python: грейд | C# (по описанию): балл | C# (по описанию): грейд | Грейд совпал |
|---|---|---|---|---|---|
| ООО «Ромашка»: устойчивые финансы (`demo-good`) | 95 | A | 100 | A | да |
| ИП Кузнецов: заметная долговая нагрузка (`demo-medium`) | 55 | C | 55 | C | да |
| ООО «Вектор»: крупная сумма (`demo-manual`) | 75 | B | 75 | B | да |
| ООО «Закат»: просрочки и налоговый долг (`demo-bad`) | 20 | E | 0 | E | да |
| ООО «Север»: не хватает данных (`demo-incomplete`) | 40 | D | 70 | B | нет |

Грейд совпал у 4 из 5 компаний. Исключение: `demo-incomplete` (не хватает расходов, платежей по кредитам и ответа БКИ):
Python даёт D, а C# по описанию посчитал бы B по оставшимся данным. Но у backend заявка без ответа БКИ в любом случае уходит менеджеру,
поэтому итог для клиента один и тот же. Баллы у двух компаний совпали случайно, у остальных различаются: шкалы разные, поэтому согласуем только грейд, а не балл.

`demo-manual` получает B в обоих расчётах, но на ручное рассмотрение уходит из-за суммы выше лимита автоодобрения продукта (20 млн при лимите 5 млн).
Это решает backend, скоринг тут ни при чём.

## 2. Почему на других данных грейды расходятся

На 12 синтетических примерах из `data/samples.json` грейды различаются в **8 случаях из 12**. Причины:

| | Python (`rules-0.2`) | C# (`rules-v1`, по описанию) |
|---|---|---|
| Расходы к выручке | есть: <70% +15, 70–90% −5, >90% −20 | нет: расходов в расчёте не видит |
| Долговая нагрузка | <0,3: +20; 0,3–0,7: 0; >0,7: −20 | <0,3: +10; 0,3–0,5: 0; 0,5–0,7: −10; ≥0,7: −25 |
| Выручка к сумме кредита | не используется | ≥4: +15; 2–4: +5; 1–2: −5; <1: −20 |
| БКИ, ФНС, ФССП | не используются, только предупреждения `*_missing` | кредитная история, налоговый долг, ФССП дают баллы (для чистой компании +20) |
| Возраст бизнеса | <6 мес. −20; 6–11 −10; 12–36 0; >36 +10 | то же самое |
| Нехватка данных | выручка, расходы или платежи отсутствуют: балл 40, грейд D | факторы без данных пропускаются, расчёт идёт дальше |
| Ровно 0,70 нагрузки | средняя (0) | высокая (−25) |

Самый опасный случай: нет расходов и платежей по кредитам, но есть ответы проверок. Python вернёт D (менеджер),
а C# посчитает по остатку и может выдать A. В таблице ниже это `missing-2`.

| Пример | Python | C# (по описанию) | Грейд совпал |
|---|---|---|---|
| `stable-1` | 95 / A | 100 / A | да |
| `stable-2` | 95 / A | 100 / A | да |
| `stable-3` | 95 / A | 100 / A | да |
| `highload-1` | 25 / E | 60 / C | нет |
| `highload-2` | 35 / D | 70 / B | нет |
| `highload-3` | 65 / B | 75 / B | да |
| `missing-1` | 40 / D | 25 / E | нет |
| `missing-2` | 40 / D | 85 / A | нет |
| `missing-3` | 40 / D | 50 / C | нет |
| `thinmargin-1` | 20 / E | 70 / B | нет |
| `thinmargin-2` | 0 / E | 60 / C | нет |
| `thinmargin-3` | 75 / B | 100 / A | нет |

## 3. Что я предположил при чтении описания (нужно проверить по коду C#)

1. «Выручка к сумме кредита» считается по **годовой** выручке за 12 месяцев.
2. Если чистая прибыль неизвестна, месячная прибыль = 10% **месячной** выручки (годовая / 12).
3. Если чистая прибыль ноль или меньше, нагрузка получает −25 (в описании про это ничего нет).
4. Если нет `monthly_debt_payments_rub`, фактор нагрузки пропускается.
5. Заблокированные счета в ФНС дают дополнительно −15 к налоговому фактору.

## 4. Варианты, как сделать грейды одинаковыми

- **A. Согласовать только демонстрационные компании** (то, что сделано). Четыре из пяти дают один грейд, пятая уходит менеджеру в обоих случаях.
  Минус: на произвольных данных грейды расходятся (см. раздел 2).
- **B. Привести Python к `rules-v1`**: взять те же факторы, пороги и баллы, читать блоки `checks`. Грейды совпадут всегда, но расчёт перестанет
  использовать расходы (это пункт задания «соотношение выручки и расходов») или будет добавлять его сверх `rules-v1`, и тогда снова расхождения.
  Нужно решение продакта и бэкендера, версия поднимется до `rules-0.3`.
- **C. Научить резервный расчёт видеть расходы.** Backend добавляет фактор «расходы к выручке» с теми же порогами, что у Python. Проще для согласованности, сложнее для backend.

Для вечерней демонстрации хватит варианта A. Если нужно, чтобы грейды совпадали всегда, выбирайте B или C.
