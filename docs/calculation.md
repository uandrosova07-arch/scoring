# Как считается оценка риска

Для всей команды. Сервис `scoring` смотрит на финансы компании и возвращает балл от 0 до 100, грейд от A до E
и список факторов с пояснениями. Кредитное решение принимает backend (C#) по политике банка и грейду.
Если `scoring` недоступен, backend считает по встроенным правилам и помечает результат как fallback.

Расчёт построен на правилах, а не на обученной модели: одинаковые данные всегда дают одинаковый ответ.

## Как набирается балл

Старт 50 баллов. Каждый фактор добавляет или убирает баллы, итог ограничивается диапазоном 0..100.

| Фактор | Условие | Баллы |
|---|---|---|
| Расходы к выручке | меньше 70% | +15 |
| | 70–90% | −5 |
| | больше 90% | −20 |
| Кредитная нагрузка | меньше 30% | +20 |
| | 30–70% | 0 |
| | больше 70% | −20 |
| | нет чистой прибыли за 12 месяцев | −35 |
| Возраст бизнеса | меньше 6 месяцев | −20 |
| | 6–11 месяцев | −10 |
| | 12–36 месяцев | 0 |
| | больше 36 месяцев | +10 |

Кредитная нагрузка: (текущие платежи по кредитам за месяц + новый платёж) / месячная чистая прибыль.
Новый платёж берётся из запроса (`estimated_monthly_payment_rub`, аннуитет считает backend), а если его нет, считается как сумма / срок.
Чистая прибыль берётся из запроса, а если её нет, считается как выручка минус расходы.

## Грейды (таблица backend)

| Грейд | Балл | Что делает backend |
|---|---|---|
| A | 80–100 | автоодобрение на запрошенных условиях, если сумма в лимите продукта |
| B | 65–79 | автоодобрение, ставка +1,5 п.п. |
| C | 50–64 | одобрение с изменёнными условиями |
| D | 35–49 | ручное рассмотрение менеджером |
| E | 0–34 | отказ |

## Если данных не хватает

Нужны три показателя: выручка, расходы и ежемесячные платежи по кредитам. Если хотя бы одного нет, оценку по неполным
цифрам не строим: возвращаем балл 40 и грейд D, чтобы заявку рассмотрел менеджер. Недостающие поля перечислены
в `missing_data`, а в факторах есть «Достаточность данных». Остальные факторы в этом случае показаны с нулевым вкладом.

## Что в ответе

- `factors`: от 3 до 7 факторов по убыванию модуля вклада. У каждого есть код, название, вклад в баллах, значение
  (например, «63%») и пояснение простым языком для клиента.
- `warnings`: например `credit_bureau_missing`, если блок внешней проверки не пришёл.
- `probability_of_default`: всегда `null`, потому что правила не откалиброваны на дефолтах.

## Упрощения

- Внешние проверки (ЕГРЮЛ, ФНС, БКИ, ФССП) в расчёте пока не участвуют: стоп-факторы по ним проверяет backend.
- Баллы и пороги предварительные, их нужно согласовать с продактом и бэкендером как условия демонстрации.

## Версии правил

Версия зашита в код (`app/rules.py`, константа `MODEL_VERSION`) и возвращается в поле `model_version`. Любое изменение баллов
или порогов меняет версию и добавляет строку в эту таблицу.

| Версия | Что это |
|---|---|
| `rules-0.1` | Первый набросок до появления контракта backend, с собственным плоским форматом. Не использовалась в интеграции |
| `rules-0.2` | Текущая. Контракт backend (`POST /api/v1/score`), балл 0..100 и грейд A–E, факторы с пояснениями |

Сравнение с резервными правилами backend: [grade-comparison.md](grade-comparison.md).
