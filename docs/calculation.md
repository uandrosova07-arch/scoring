# Как считается оценка риска (rules-0.3)

Для всей команды. Сервис `scoring` смотрит на финансы компании и внешние проверки и возвращает балл от 0 до 100,
грейд от A до E, вероятность дефолта и список факторов с пояснениями. Кредитное решение принимает backend (C#)
по политике банка и грейду.

`rules-0.3` — общие правила сервиса и резервной модели backend (`RuleBasedScoringService`). За основу взяты
резервные правила `rules-v1`, которые бэкендер подтвердил тестами, плюс согласованное правило для расходов.
Если обе стороны считают по `rules-0.3`, то на одном и том же запросе они дают один и тот же ответ: балл, грейд, PD,
факторы с текстами, предупреждения. Значит, и решение банка не зависит от того, ответил ли сервис.
Проверка: общий эталон `data/conformance/rules-0.3.json`, его гоняют `tests/test_conformance.py` и C#-тест backend.

## Как набирается балл

Старт 50 баллов. Каждый фактор добавляет или убирает баллы, итог ограничивается диапазоном 0..100.
Границы указаны точно: «≥ 4» значит, что ровно 4 уже даёт +15.

| Код | Фактор | Условие | Баллы |
|---|---|---|---|
| `business_age` | Возраст бизнеса, полных месяцев | < 6 | −20 |
| | | 6–11 | −10 |
| | | 12–35 | 0 |
| | | ≥ 36 | +10 |
| `revenue_to_amount` | Годовая выручка / сумма кредита | ≥ 4 | +15 |
| | | ≥ 2 и < 4 | +5 |
| | | ≥ 1 и < 2 | −5 |
| | | < 1 | −20 |
| `expense_ratio` | Годовые расходы / годовая выручка | ≤ 0,90 | 0 |
| | | > 0,90 | −10 |
| `debt_load` | (текущие платежи по кредитам + новый платёж) × 12 / годовая прибыль | < 0,3 | +10 |
| | | ≥ 0,3 и < 0,5 | 0 |
| | | ≥ 0,5 и < 0,7 | −10 |
| | | ≥ 0,7, или прибыль ≤ 0 | −25 |
| `credit_history` | БКИ, максимальная просрочка за 24 месяца | нет истории (0 месяцев, 0 кредитов) | 0 |
| | | без просрочек | +15 |
| | | 1–30 дней | −5 |
| | | 31–90 дней | −15 |
| | | > 90 дней или списания | −30 |
| `tax_debt` | ФНС, налоговая задолженность | нет (0) | +5 |
| | | < 50 000 ₽ | −5 |
| | | ≥ 50 000 ₽ | −15 |
| | | плюс заблокированные счета | ещё −15 |
| `enforcement` | ФССП, открытые производства | нет | 0 |
| | | есть | −10 |
| `collateral` | Клиент предложил залог | да | +10 |

Новый платёж `estimated_monthly_payment_rub` считает backend (аннуитет по базовой ставке продукта). Нагрузка считается
одним делением, поэтому значения ровно на границах 0,3, 0,5 и 0,7 не зависят от округления.

### Расходы

Расходы учитываются в двух местах, одинаково в Python и C#:

1. **Фактор `expense_ratio`, только штраф.** Если расходы больше 90 % выручки, запас прочности у бизнеса маленький: −10.
   Бонуса за низкие расходы нет: прибыль уже очищена от расходов, и бонус посчитал бы их второй раз через нагрузку.
   На демо-компаниях правило не меняет ни одного балла.
2. **Прибыль, если чистая прибыль не пришла**: выручка − расходы.

## Грейды (таблица backend)

| Грейд | Балл | Что делает backend |
|---|---|---|
| A | 80–100 | автоодобрение на запрошенных условиях, если сумма в лимите продукта |
| B | 65–79 | автоодобрение, ставка +1,5 п.п. |
| C | 50–64 | одобрение с изменёнными условиями: сумма до 25 % годовой выручки, ставка +3 п.п. |
| D | 35–49 | ручное рассмотрение менеджером |
| E | 0–34 | отказ |

Вероятность дефолта: `0,02 + (100 − балл) / 100 × 0,30` (от 2 % при 100 баллах до 32 % при 0). Это эвристика backend,
а не калибровка на дефолтах; сервис возвращает то же число, чтобы карточка менеджера не зависела от источника.

## Если данных не хватает

Правило как у backend: фактор, для которого нет данных, не считается, в ответ добавляется предупреждение,
расчёт продолжается по остальному. Отдельного «грейда для нехватки данных» больше нет.

| Нет | Что происходит | `warnings` |
|---|---|---|
| `expenses_rub` | фактора `expense_ratio` нет | `expenses_missing` |
| `net_profit_rub` | прибыль = выручка − расходы, а если нет и расходов, 10 % выручки | `net_profit_missing` |
| блок `credit_bureau`, `fns`, `fssp` | нет фактора `credit_history`, `tax_debt`, `enforcement` | `credit_bureau_missing`, `fns_missing`, `fssp_missing` |
| блок `egrul`, `fns.reported_revenue_rub` | в баллах не участвуют | — |

Предупреждения идут в порядке расчёта: расходы, прибыль, БКИ, ФНС, ФССП. `missing_data` перечисляет пути полей,
пришедших как `null`, в том же порядке, что и backend: `company.financials.expenses_rub`, `company.financials.net_profit_rub`,
`checks.egrul`, `checks.fns` (или `checks.fns.reported_revenue_rub`), `checks.credit_bureau`, `checks.fssp`.

Без выручки, текущих платежей по кредитам, возраста бизнеса, суммы, срока и нового платежа расчёт невозможен.
Backend присылает их всегда (в C# эти поля не nullable), поэтому `null` или отсутствие такого поля — ошибка запроса: `400`.

Что в итоге решит backend, зависит от пропуска: без ЕГРЮЛ или БКИ заявка уходит менеджеру ещё до скоринга, а без ФНС или ФССП
политика отправляет её менеджеру после скоринга при любом грейде (если нет стоп-факторов).

## Что в ответе

- `factors`: от 3 до 8 факторов (восьмой только при залоге) по убыванию модуля вклада, при равенстве по коду.
  У каждого: `code` без префикса, `title`, `impact` в баллах, `value` для карточки менеджера и `client_explanation` для клиента.
  Тексты совпадают с C# дословно. Backend сам добавляет `factor_` к коду в причинах решения (`factor_debt_load`).
- `value`: месяцы как «7 г. 7 мес.», отношения с точкой («32.0x», «0.85», «0.48»), суммы «12 000 ₽»; при нагрузке ≥ 9,99
  или прибыли ≤ 0 — «прибыль отсутствует». Округление половины от нуля, как форматирование .NET.
- `warnings`, `missing_data`: см. выше. `model_version`: `rules-0.3`.

## Пример: ООО «Ромашка» из seed backend

Оборотный кредит 1 500 000 ₽ на 12 месяцев, запрос `data/requests/demo-good.json`.

| Фактор | Расчёт | Баллы |
|---|---|---|
| Старт | | 50 |
| Кредитная история | 60 месяцев, без просрочек | +15 |
| Выручка к сумме | 48 000 000 / 1 500 000 = 32,0 | +15 |
| Возраст бизнеса | с 12.03.2019, на 23.10.2026 это 91 месяц (7 г. 7 мес.) | +10 |
| Налоги | задолженности нет | +5 |
| Нагрузка | (150 000 + 138 593) × 12 / 7 200 000 = 0,48 | 0 |
| ФССП | производств нет | 0 |
| Расходы к выручке | 40 800 000 / 48 000 000 = 0,85, не больше 0,90 | 0 |
| Итог | | **95, грейд A, PD 0,035** |

Backend одобряет 1,5 млн под 19,5 %, платёж 138 593,06 ₽. Все пять демо-заявок и решения: [grade-comparison.md](grade-comparison.md),
ответы сервиса: [score-examples.md](score-examples.md).

## Версии правил

Версия зашита в код (`app/rules.py`, константа `MODEL_VERSION`) и возвращается в поле `model_version`. Любое изменение
факторов, порогов, текстов или обработки пропусков меняет версию в обоих репозиториях сразу и пересобирает эталон
(`python scripts/conformance.py build`).

| Версия | Что это |
|---|---|
| `rules-0.1` | Первый набросок до появления контракта backend, с собственным плоским форматом. Не использовалась в интеграции |
| `rules-0.2` | Свои факторы (расходы, нагрузка, возраст), коды с префиксом `factor_`, балл 40 / D при нехватке данных. На данных seed ломала два сценария демо |
| `rules-0.3` | Текущая. Общие правила с резервной моделью backend: факторы и пороги `rules-v1` плюс правило для расходов, коды без префикса, PD по формуле backend |
