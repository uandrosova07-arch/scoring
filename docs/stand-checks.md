# Сквозные проверки общего стенда

Проверяем полный процесс на общем стенде (backend + scoring + PostgreSQL) в двух режимах:

- **External / rules-0.3**: отвечает сервис scoring;
- **RulesFallback / rules-0.3**: scoring остановлен, backend считает резервными правилами (после переноса в C# это та же версия).

Положительные сценарии проходят весь путь клиента: решение → предложение → принятие → договор → демо-код → подписание → `Disbursed`.

**С logreg-synthetic-0.1.** Новые образы scoring по умолчанию отвечают `logreg-synthetic-0.1`, а резервные правила backend пока
rules-0.3. Скрипт экспортирует `SCORING_MODEL=rules-0.3`, но контейнер получит её, только если compose передаёт эту переменную
сервису `scoring` (как в `docs/backend/compose.scoring.yml`). Иначе нужен тег образа с rules-0.3. Проверка: `curl localhost:18000/health`
должен показать `rules-0.3`, иначе External упадёт на сверке версии. Переход на logreg: [backend/logreg.md](backend/logreg.md).

## Запуск

Репозитории `probiinik` и `scoring` лежат рядом. Нужны Docker с Compose v2 и Python 3.12+ (зависимости не нужны).

```bash
cd scoring
BACKEND_DIR=../probiinik scripts/run_stand_checks.sh
```

Скрипт поднимает **отдельный compose-проект `alfacredit-e2e`**: своя база в томе `alfacredit-e2e_db-data`, свои контейнеры,
порты API 18080, scoring 18000, PostgreSQL 15432. Рабочий стенд (`alfacredit`, том `alfacredit_db-data`, порт 8080) не останавливается
и не сбрасывается. Перед прогоном и после него удаляется только том тестового проекта, поэтому seed и демо-заявки всегда с нуля.
Имя `alfacredit` скрипт использовать отказывается.

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `BACKEND_DIR` | `../probiinik` | репозиторий backend |
| `E2E_PROJECT` | `alfacredit-e2e` | имя тестового compose-проекта |
| `E2E_API_PORT`, `E2E_SCORING_PORT`, `E2E_POSTGRES_PORT` | 18080, 18000, 15432 | порты тестового стенда |
| `E2E_OUT` | `e2e-results/<время UTC>` | куда сложить отчёты |
| `E2E_COMPOSE_OVERRIDE` | нет | дополнительный compose-файл (например, `docs/backend/compose.scoring.yml` для старой версии backend с заглушкой) |
| `KEEP=1` | нет | оставить тестовый стенд после прогона |
| `DRY_RUN=1` | нет | только показать команды |

Что делает скрипт: `down -v` тестового проекта → `up -d --build` → ожидание `/health/ready` → версии образов →
`e2e_backend.py --mode External` → `docker compose stop scoring` → `e2e_backend.py --mode RulesFallback` → `start scoring` →
`down -v` тестового проекта. Код выхода 0, если оба прогона прошли.

Один режим против уже запущенного стенда:

```bash
python scripts/e2e_backend.py --api http://localhost:18080 --scoring http://localhost:18000 --mode External --report external.md
```

## Сценарии и ожидаемые результаты

Данные seed backend, суммы и сроки как в общем демо (`data/demo_companies.json`). Ожидаемое одинаково в обоих режимах.

| Сценарий | Клиент, заявка | Скоринг | Решение | Дальше | Что проверяется |
|---|---|---|---|---|---|
| **approve**: обычное одобрение | `client_good`, оборотный, 1 500 000 ₽ на 12 мес. | 95 / A | одобрено 1 500 000 ₽ под 19,5 %, 138 593,06 ₽/мес | принятие → договор → код → подпись → `Disbursed` 1 500 000 ₽ | сумма, ставка и платёж в решении, предложении и договоре; 12 строк графика; выдача `Completed`, платёжное поручение |
| **reduced**: меньшая сумма с объяснением | `client_medium`, оборотный, 3 000 000 ₽ на 24 мес. | 55 / C | с условиями: 2 400 000 ₽ под 22,5 %, 125 100,96 ₽/мес, причина `amount_reduced` с текстом | тот же путь, `Disbursed` 2 400 000 ₽ | сумма меньше запрошенной, есть объяснение и условия, договор и выдача на 2 400 000 ₽ |
| **reject**: отказ | `client_bad`, экспресс, 500 000 ₽ на 6 мес. | 0 / E | отказ: `tax_debt`, `accounts_blocked`, `overdue_90`, `enforcement_debt` с пояснениями | дальше пути нет | предложения нет; нет `acceptOffer`/`signContract`; принять — 409; договора нет — 404; кода нет — 404/409; статус остаётся `Rejected`, выдачи нет |
| manual (справка) | `client_manual`, оборотный, 8 000 000 ₽ на 24 мес. | 70 / B | менеджер, рекомендация «одобрить» | демо-менеджер 50/50, не идём | только решение автоматики |
| submission (справка) | `client_new`, экспресс, 300 000 ₽ на 12 мес. | — | `400` при подаче: бизнесу 4 месяца | — | заявка не создаётся |

В каждом сценарии со скорингом по карточке менеджера проверяется `scoring.source` (= режим), `scoring.modelVersion` (= `rules-0.3`),
балл и грейд; в RulesFallback ещё предупреждение `external_scoring_unavailable`. Демо-код берётся из ответа API, а если он скрыт
(`CONTRACTS_REVEAL_CODE=false`), из ленты событий, как его видит клиент.

## Что фиксирует отчёт

`e2e-external.md` / `e2e-rulesfallback.md` (и JSON с теми же данными) содержат: время, адрес API, дату демо-данных,
`/health` сервиса scoring (версия правил), `/health/ready` backend с состоянием каждой проверки, версию OpenAPI;
по каждому сценарию вход (клиент, продукт, сумма, срок), скоринг (балл, грейд, PD, источник, версия), решение, итог
(номер договора, сумма выдачи, платёжное поручение) и все проверки с результатом. Скрипт стенда дополнительно сохраняет
`images.txt` (образы и их ID) и `containers.json`.

## Где это проверено

| Где | External / rules-0.3 | RulesFallback / rules-0.3 |
|---|---|---|
| Фейковый backend по контракту API (`tests/support/fake_backend.py`, `tests/test_e2e_script.py`) | 5 сценариев прошли, approve и reduced дошли до `Disbursed`, reject остановлен | то же |
| Общий стенд | `scripts/run_stand_checks.sh`, результат в `e2e-results/` | то же |

Тесты на фейке также проверяют, что скрипт **падает**, если источник не тот, если резервные правила всё ещё `rules-v1`
и если отклонённую заявку можно довести до договора.

## Ограничения

- Фейковый backend — модель API по `docs/api.md` и `docs/completion-flow.md` backend (коммит `9f18dd4`), а не сам backend.
  Подтверждением служит только прогон на стенде.
- Сценарий manual не доводится до конца: ответ демо-менеджера случайный (`DemoManager:ApprovalProbability = 0.5`).
- Демо-данные рассчитаны на 23.10.2026. Возраст бизнеса растёт; у seed-компаний до порогов далеко, кроме ИП Петровой:
  с 15.12.2026 ей станут доступны экспресс и овердрафт, и сценарий submission перестанет давать `400`.
- Тестовый стенд собирает образы с теми же тегами, что рабочий (`alfacredit-api:local`, `alfacredit-scoring:local`):
  работающие контейнеры не меняются, но при следующем `up` рабочий стенд возьмёт пересобранный образ.
- Режим RulesFallback проверяется остановкой контейнера scoring. Таймаут, `5xx` и `4xx` от scoring не моделируются: их проверяют
  `HttpScoringServiceTests` backend.
